【一句话结论】
  成功的关键不是"改模型"本身（那部分早就对了），而是【CRILAYLA 压缩打包必须零填充】：
  data.cpk 里每个文件的 FileSize 必须精确等于 CRILAYLA 的 (16 + cs + 0x100)。
  之前为了"保持原 FileSize=399636"给压缩流补了 288 字节零 → 文件自相矛盾 → 游戏拒绝载入
  → 表现就是"选香磷进不了战斗"。去掉补零、FileSize 用压缩流精确长度后，一次通过。

--------------------------------------------------------------------------------
【2. 根因：为什么折腾了很久才成（血的教训）】
--------------------------------------------------------------------------------
  ★ 症状：换模后"选香磷进不了战斗"（黑屏/卡住），但"内容一字不改、只是重新打包"的
    对照 ISO 能正常进战斗。
  ★ 曾误判：以为是"游戏对文件内容做 CRC 完整性校验"，于是花大量时间逆向 TOC 里的
    CRC 字段（试遍 CRC32 目录 / md5 / sha / FNV / Jenkins / Murmur / xxHash /
    GF(2) 差分 GCD 判断是否多项式 CRC）。—— 全是弯路。

  ★ 真因（决定性证据）：
    遍历原版 data.cpk 里全部 1213 个 CRILAYLA 文件，**FileSize 全部精确等于
    (16 + cs + 0x100)**，一个补零的都没有。
      文件头：'CRILAYLA'(8) + UncompressedSize(u32) + CompressedSize(即 cs)(u32)
              + 压缩流(cs 字节，倒序位流) + 原始前 0x100 字节
      ⇒ 文件总长 = 16 + cs + 0x100。
    而之前为了让 FileSize 保持 399636（原版值），把压缩流补零到 399636 —— 但压缩流的
    精确长度只有 399348（我的压缩器比原厂压得更狠）→ FileSize(399636) ≠ 16+cs+0x100(399348)
    → 文件头尾自相矛盾 → 游戏判定非法 → 拒绝载入。

  ★ 为什么"对照 ISO 能进"：对照 ISO 用的是**原版未重压**的压缩字节（长度本来就精确），
    所以它没问题；所有失败版本（mod/black/flip/flipB）**都带了补零**。
    → 之前基于 flipB 得出的"CRC 字段被校验"结论，是被补零这个混淆因素污染了，作废。

  ★ 正确做法：**绝对不要补零**。
      FileSize   = 我的压缩流精确长度 (16+cs+0x100)
      ExtractSize= 解压后的真实长度（改模后会变小，本案 640108 → 634564）
    （补零是为了"保持原尺寸"这个错误执念；尺寸本来就该随内容变。）

【3. 换模本身怎么做（这部分是标准操作）】
--------------------------------------------------------------------------------
  用 ccsLib 读入香磷 CCS（基底）与天天 CCS（来源），只替换"外观相关块"：

  (1) body Model：香磷 'MDL_2kar00t0 body'（idx 1710）
        - 把它的 meshes 换成天天的（deepcopy 天天 'MDL_2tew00t0 body' idx 2273 的 meshes）
          两者均为 DeformableMesh、17 个 mesh、vertexScale=256.0、meshCount 相同
        - 每个 mesh 的 materialIndex 由 2274（天天 MAT_clut）改为 1711（香磷 MAT_clut）
        - lookupList 用天天的（20 项），lookupListCount=20

  (2) body 贴图：香磷 'TEX_2karbody'（idx 1712）
        - textureData 换成天天 'TEX_2tewbody'（idx 2275）的
          两者同为 Indexed8(0x13) 128x256，32768 字节像素数据
        - textureType/width/height 完全一致，直接搬运
        - 校验：md5(改后 TEX_2karbody) == md5(TEX_2tewbody) == 56455bcf464ff043...

  (3) 调色板 CLUT：香磷 body CLUT（idx 1744，256 色）
        - paletteData 换成天天 body CLUT（idx 2356）的（同样 256 色）

  (4) 其余一律不动：骨架 OBJ_2kar00t0 / CMP_2kar00t0 trall、全部 Animation、
      Material、名字表、Stream、其他 Model（脚/木/玉/眼镜等）全部保留香磷的。

  ★ 为什么跨骨架能直接搬 mesh 顶点数据：
     顶点里的 boneID 是"Clump.boneIndices 数组的下标(pos)"，不是骨名编号。
     香磷与天天的骨架 pos→骨名映射完全一致（25 骨；pos0=trall根, pos3=pelvis,
     pos13=head, pos23=r finger0, pos24=body ...），且 mesh 顶点存的是 pos 号，
     所以天天的顶点在香磷骨架上语义相同 → **顶点数据一个字节都不用改**，
     只需要把 materialIndex / lookupList / 贴图 / 调色板 改掉。

  ★ 自检通过标准：
     - 块数=3211、结构与香磷一致
     - body mesh 顶点数 == 天天的 [18,38,8,30,14,6,78,829,26,24,70,4,78,61,28,24,687]
     - TEX_2karbody 像素 md5 == 天天 body 贴图 md5
     - 全部 mesh.materialIndex == 1711
     - 与香磷原文件的字节差异只落在 body Model 区 + body 贴图/CLUT 区

【4. ccsLib 必须先修成"逐字节无损"（前提工程）】
--------------------------------------------------------------------------------
  若 CCS 读写器有损，即使换对了模型，重写出的字节也与原版有别，风险不可控。
  本次先把 ccsLib 修到 **roundtrip(原香磷)==原字节、roundtrip(原天天)==原字节**：
    (a) Animation 帧子块编号 off-by-one：原版 Frame 块号是"下一帧"语义
        （写 current_frame+1），ccsLib 原来写 current_frame。          [Anms.py]
    (b) 法线缩放：读用 1/127 而写用 ×64（≈0.5，法线半值破坏）→ 读改 1/64。[ccsModel.py]
    (c) RigidMesh 颜色读取 ×2+clamp、写出 /2 → 损失位；改原样存取。   [ccsModel.py]
    (d) CLUT 调色板 alpha 读取 ×2+clamp、写出 /2 → 改原样存取。       [ccsClut.py]
    (e) 多权重法线写出永远取 slot0 → 改按 slot i 取。                 [ccsModel.py]
    (f) objectFrame 写出的掩码误用十进制(10/20/40/80/100/200/400/800)
        → 改十六进制(0x10/0x20/...)。                                 [Anms.py]
    (g) 写入时保留 chunk 的原始 size 字段（原 Model 1710 的 size 字段比内容
        多算 0xFF 单位=1020B；游戏不按 size 字段走块，保留原值最稳）。  [ccs.py]
  验收：_rt.py 对两个原文件 roundtrip，_diff.py 差异必须为 0。

【7. 排错速查 & 反模式】
--------------------------------------------------------------------------------
  ✔ 症状"选角色进不了战斗" → 先查 CPK 里被改文件的 FileSize 是否 == 16+cs+0x100。
     99% 是补零了（或压缩流自相矛盾）。
  ✔ 症状"能进但外观没变" → 该文件不是该画面真正的渲染源；去定位真正的 body 源。
  ✔ 做对照实验时**一次只改一个变量**：本次 flipB 想测"CRC 字段"，却同时换了压缩流
     （重压+补零），导致把补零误判成 CRC 校验，白绕大圈。
  ✘ 不要为"保持原 FileSize/ExtractSize"而补零 —— 尺寸本就该随内容变。
  ✘ 不要动 chunk 的 size 字段去"对齐"——保留原值。
  ✘ 别用"整文件替换"思路之外的重建方式破坏 CPK 布局；重建 CPK 本身没问题
     （对照 ISO 证明重建 OK），问题只在 CRILAYLA 文件本身的自洽性。
